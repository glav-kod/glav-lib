# Git workflow

## Commit messages

Сообщение коммита в формате Conventional Commits.

- **Язык:** `summary` и тело — на **русском**; `<type>`/`<scope>`, ключ задачи и технические
  идентификаторы (имена файлов, символов, команд) — на английском.
- **Формат:** `<type>(<scope>): <summary>`; с ключом задачи — `<issue-key>: <type>(<scope>): <summary>`.
  Ключ задачи (`POW-123`, `PROJ-456`, `#123`) добавляй, если он есть в ветке/контексте.
- **Scope** — затронутая сборка или подсистема в том виде, как она называется в репозитории:
  `basics`, `abstractions`, `app`, `db`, `source-generators`, `sandbox`, `migrations`, `build`.
- **Summary:** ≤ 72 символов, с заглавной буквы, без точки в конце, описывает суть (что и зачем),
  а не «поправил».
- Сообщение основывай на реальном diff (`git diff --cached` / `git diff`).

```bash
git commit -m "fix(db): исправлено освобождение соединения при откате транзакции"
git commit -m "PROJ-123: feat(source-generators): поддержка необязательных аргументов ошибок"
```

## Понятный язык в коммитах и PR

Общее требование к тексту коммитов и pull request'ов: их читает коллега, который **не видел diff**
и **не участвовал в сессии**. Из текста должно быть ясно, что изменилось и зачем, без чтения кода.

- **Пиши суть, а не факт правки.** «Поправил», «пофиксил», «мелкие правки», «рефакторинг»,
  «обновление» — так писать нельзя: это не несёт информации. Назови конкретное поведение,
  правило или контракт, который изменился.
- **Полные предложения.** Не телеграфный стиль, не цепочки стрелок (`A → B → C`),
  не обрывки вида «фикс сериализации».
- **Смысл, а не пересказ diff.** Не перечисляй построчно, какие файлы тронуты, — это видно в diff.
  Объясняй, какая задача решена и почему выбран такой способ, если он неочевиден.
- **Никаких отсылок к чату и процессу.** «Как обсуждали», «по просьбе», «по замечаниям ревью»,
  «часть 2» — читатель истории этого контекста не имеет. Пиши так, чтобы текст был самодостаточным.
- **Технические идентификаторы** (имена файлов, классов, методов, команд, таблиц) оставляй
  на английском и оформляй бэктиками — переводить их не нужно.

```bash
# плохо — не видно, что изменилось
git commit -m "fix(basics): поправил сериализацию"
git commit -m "refactor(db): мелкие правки после ревью"

# хорошо — понятно, что и зачем
git commit -m "fix(basics): UtcDateTime разбирает строку без смещения как UTC"
git commit -m "refactor(db): выбор строки подключения вынесен в DbSessionFactory"
```

## Изменения публичного API

Библиотека выходит пакетами NuGet, поэтому её публичные типы — контракт с чужим кодом,
который агент не видит. Если правка меняет сигнатуру, поведение или состав публичного типа,
скажи об этом отдельной строкой в теле коммита и в описании pull request'а: назови сломанный
контракт и то, что потребитель должен сделать при обновлении.

Совместимое расширение (новая перегрузка, новый тип, новый необязательный параметр) такой
пометки не требует.

## Pull Requests

PR создавай и обновляй на **русском языке** — подробнее в `.claude/rules/language-russian.md`.
Требования к понятности из раздела выше применяй к заголовку и описанию PR полностью.

- **Заголовок PR** формулируй по тем же правилам, что и summary коммита (Conventional Commits,
  ≤ 72 символа): при squash merge он становится сообщением коммита в `main`.
- **Описание PR** должно отвечать на три вопроса: что изменилось, зачем это понадобилось,
  как проверяли. Шаблона pull request'а в репозитории нет, поэтому оформляй описание
  тремя разделами — «Что изменилось», «Зачем» и «Как проверяли», — а не произвольным текстом.
- Если изменение затрагивает публичный API библиотеки, схему базы данных или поведение
  source-генераторов, скажи об этом в описании явно, отдельным абзацем.
- В разделе «Как проверяли» указывай реальные запущенные команды и их результат
  (`dotnet build GlavLib.sln -c Debug`, конкретный `dotnet test ...`), а не общие слова
  о том, что всё работает. Проверки, которые в облачной среде выполнить нельзя (всё, что
  требует Postgres), перечисли как непроверенное.
- Описание основывай на реальном diff ветки (`git diff <базовая-ветка>...HEAD`), а не на памяти
  о сессии.
- Если pull request для рабочей ветки ещё не создан — **создай** его; если он уже есть —
  **обнови** заголовок и описание под текущий diff ветки, а не под первоначальный замысел.
- Операции с pull request выполняй инструментами GitHub MCP (`mcp__github__*`).

### Базовая ветка pull request'а

Прежде чем вызывать инструменты GitHub MCP, определи базовую ветку pull request'а.
Подставлять `main` по умолчанию нельзя: рабочая ветка сессии не всегда отведена от `main`,
а при неверной базе в pull request попадают чужие коммиты базовой ветки, и его diff перестаёт
соответствовать сделанной работе.

Базовая ветка — та, от которой отведена рабочая ветка сессии. Определяй её по фактическому
состоянию репозитория, а не по предположению:

- `git reflog` показывает, на какой ветке контейнер стартовал и с чего была создана рабочая ветка;
- `git branch --contains <коммит>` (и `git branch -r --contains <коммит>`) показывает, каким веткам
  принадлежит коммит, от которого отведена рабочая ветка;
- `git merge-base <кандидат> HEAD` показывает точку расхождения с веткой-кандидатом и тем самым
  подтверждает или опровергает догадку.

Перед проверкой выполни `git fetch origin`: по устаревшим удалённым веткам вывод этих команд
вводит в заблуждение.

Явное указание базовой ветки пользователем или инструкциями сессии имеет приоритет над этим
выводом — в таком случае бери названную ветку и репозиторий не опрашивай.

Если после проверки базовая ветка всё равно неоднозначна, спроси пользователя. Молча выбирать
`main` в такой ситуации нельзя.

При обновлении уже существующего pull request'а базовую ветку тоже сверяй с рабочей веткой сессии
и, если она выбрана неверно, исправляй её (`mcp__github__update_pull_request`, поле `base`),
а не оставляй как есть.

## Merge strategy

PR нужно мержить только через **Squash and merge**.

- Не используй merge commit для PR.
- Не используй rebase merge для PR.
- Если пользователь явно просит выполнить merge, выбирай squash merge.
- Если merge выполняет человек в GitHub UI, в описании/комментариях PR при необходимости указывай ожидание: merge strategy — squash.
