# Регламент ежедневного отчёта о состоянии репозитория

Этот файл — полная инструкция для агента, который запускается по расписанию в чистой сессии.
Считай, что никакого предшествующего обсуждения не было и другого контекста у тебя нет: всё,
что нужно сделать, описано ниже. Репозиторий — `glav-kod/glav-lib`, основная ветка — `main`.

Расписание: по будням в 20:00 по Бишкеку (UTC+6), то есть в 14:00 UTC.

## 1. Назначение и адресат

Отчёт читает вся команда разработки, а не один конкретный человек. Его задача — дать за минуту
понять, что въехало в `main` за прошедшие сутки, в каком состоянии открытые pull request'ы
и какие проблемы назревают.

Пиши нейтрально и объясняюще: читатель не видел ни одного diff'а и не участвовал в обсуждениях.
Не оценивай работу коллег, не хвали и не ругай — излагай факты и называй риски.

В репозитории **не настроены GitHub Actions** (каталога `.github/workflows` нет). Поэтому сборка
и тесты, которые ты запускаешь по этому регламенту, — единственная регулярная автоматическая
проверка состояния `main`. Относись к этому разделу отчёта серьёзно.

Вторая особенность репозитория важнее первой: `GlavLib` — библиотека, которая выходит пакетами
NuGet, и её потребители живут в других репозиториях. Сломанный публичный API здесь ничем себя
не проявит — он проявится у чужого приложения при обновлении пакета. Поэтому раздел про публичный
API в отчёте обязателен, даже когда сказать нечего.

## 2. Окно отчёта

Окно — от **14:00 UTC предыдущего рабочего дня** до момента запуска.

В понедельник окно расширяется до пятницы, то есть до 72 часов назад, чтобы работа, сделанная
в выходные, не потерялась между отчётами.

```bash
git fetch origin main
if [ "$(date -u +%u)" = "1" ]; then BACK=3; else BACK=1; fi
START=$(date -u -d "-$BACK day" +%Y-%m-%dT14:00:00Z)
BASE=$(git rev-list -1 --before="$START" origin/main)
echo "Начало окна: $START, базовый коммит: $BASE"
```

**Базовый коммит окна — это последний коммит, сделанный ДО начала окна**, и сравнивать `origin/main`
нужно именно с ним. Соблазн взять «последний вчерашний коммит» и сравнивать с ним приводит к тому,
что сам этот коммит и всё, что попало в `main` между ним и границей окна, из отчёта выпадает.

Клон репозитория в облачной среде может быть **неполным** (`shallow`). Если `git rev-list -1 --before=...`
вернул пустую строку, история просто не достаёт до начала окна — углуби её и повтори:

```bash
git fetch --deepen=200 origin main
BASE=$(git rev-list -1 --before="$START" origin/main)
```

Дальше во всех командах `$BASE` — это найденный базовый коммит, а `origin/main` — состояние ветки
на момент запуска.

## 3. Сбор данных

### 3.1. Общая картина

```bash
# Коммиты окна с авторами
git log --format='%h | %an | %ad | %s' --date=iso "$BASE..origin/main"

# Кто сколько коммитов сделал
git shortlog -sn --no-merges "$BASE..origin/main"

# Общий объём правок
git diff --shortstat "$BASE" origin/main
```

Разбивка по частям репозитория:

```bash
for area in "GlavLib.Abstractions" "GlavLib.Basics" "GlavLib.Db" "GlavLib.App" \
            "GlavLib.SourceGenerators" "GlavLib.SourceGenerators.Tests" "GlavLib.Tests" \
            "Sandbox" "migrations" "build"; do
  printf '%-32s %s\n' "$area" "$(git diff --shortstat "$BASE" origin/main -- $area)"
done
```

### 3.2. Публичный API

Ломающая правка публичного типа — главный риск этого репозитория, потому что здесь она
не проявляется никак. Смотри на удалённые и изменённые публичные объявления в публикуемых
сборках:

```bash
git diff -U0 "$BASE" origin/main -- 'GlavLib.Abstractions/**/*.cs' 'GlavLib.Basics/**/*.cs' \
                                    'GlavLib.Db/**/*.cs' 'GlavLib.App/**/*.cs' \
  | grep -E '^-[[:space:]]*(public|protected)' | sort -u
```

Каждая такая строка — кандидат в риск: публичный член либо исчез, либо изменил сигнатуру.
Проверь по diff'у, что произошло на самом деле, и назови в отчёте последствие для потребителя:
«из `UtcDateTime` убрана перегрузка `FromString(string)` — приложения, вызывающие её, перестанут
собираться после обновления пакета». Добавление новых публичных членов риском не является,
но в разделе про API его тоже стоит упомянуть одной строкой: это то, ради чего выпускается
новая версия.

Отдельно посмотри, не переехал ли тип между сборками и не появились ли у публикуемого проекта
новые зависимости:

```bash
git diff "$BASE" origin/main -- '**/*.csproj' Directory.Packages.props Directory.Build.props
```

Новая `PackageReference` в публикуемой сборке — это новая транзитивная зависимость у всех
потребителей, а смена версии в `Directory.Packages.props` расходится по ним всем сразу.

### 3.3. Source-генераторы

Генераторы выпускают код, который компилируется у потребителей, поэтому их правка — тоже
изменение контракта, даже если публичные сигнатуры библиотеки не тронуты.

```bash
git diff --stat "$BASE" origin/main -- GlavLib.SourceGenerators GlavLib.SourceGenerators.Tests
git diff --stat "$BASE" origin/main -- '**/_errors/*.errors.yaml'
```

Правка генератора без правки его тестов подозрительна: тесты сравнивают выпущенный код
с эталонной строкой посимвольно, и если они не менялись, значит форма выпускаемого кода
осталась прежней — либо изменение не покрыто проверкой. Скажи об этом прямо.

### 3.4. Миграции

Миграции накатываются Liquibase; `migrations/db.changelog.xml` подключает каталог `public`
директивой `includeAll`, а порядок наката внутри каталога — алфавитный по имени файла,
поэтому файлы именуются с числовым префиксом.

**Новые, изменённые и удалённые файлы миграций:**

```bash
git diff --diff-filter=A --name-only "$BASE" origin/main -- migrations   # новые
git diff --diff-filter=M --name-only "$BASE" origin/main -- migrations   # изменённые
git diff --diff-filter=D --name-only "$BASE" origin/main -- migrations   # удалённые
```

**Проверка изменённых файлов — самое важное здесь.** Правка существующего файла миграции допустима
только добавлением нового changeset в конец файла. Переписывание или удаление changeset'а, который
уже применён на чьей-то базе, ломает накат: Liquibase сверяет контрольную сумму и падает,
а откатить уже применённое изменение он не может. Такую правку надо выносить в отчёт как риск
первой величины.

Признак переписанного changeset'а — удалённые строки заголовков `--changeset` в diff'е файла:

```bash
for f in $(git diff --diff-filter=M --name-only "$BASE" origin/main -- migrations); do
  removed=$(git diff -U0 "$BASE" origin/main -- "$f" | grep -c '^---changeset')
  echo "$f: удалённых заголовков changeset = $removed"
done
```

Ненулевое значение — почти наверняка проблема, посмотри такой файл глазами:
`git diff "$BASE" origin/main -- "$f"`.

Нулевое значение ещё не гарантирует, что правка была добавлением: тело существующего changeset'а могли
изменить, не трогая его заголовок. Чтобы это увидеть, сравни позицию ханков с длиной старой версии файла —
у честного добавления в конец единственный ханк начинается на последней строке старой версии или после неё:

```bash
old=$(git show "$BASE:$f" | wc -l)
echo "строк в старой версии: $old"
git diff -U0 "$BASE" origin/main -- "$f" | grep '^@@'
```

Учти частый безобидный случай: если в старой версии файла не было перевода строки в конце, добавление
нового changeset'а даёт в diff'е одну удалённую строку и её же обратно среди добавленных. Это не
переписывание.

### 3.5. Дисциплина работы с историей

```bash
# Коммиты, попавшие в main без ссылки на pull request
git log --format='%h %s' "$BASE..origin/main" | grep -vE '\(#[0-9]+\)$'

# Коммиты, не соответствующие Conventional Commits
git log --format='%h %s' "$BASE..origin/main" \
  | grep -vE '^[0-9a-f]+ ([A-Z]+-[0-9]+: )?(build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test)(\([a-z0-9._/-]+\))?!?: '

# Revert-коммиты
git log --format='%h %s' --grep='^[Rr]evert' "$BASE..origin/main"
```

Коммит без ссылки на PR означает, что изменение уехало в `main` мимо ревью, — это стоит упомянуть,
даже если само изменение выглядит безобидным. Revert почти всегда указывает на то, что накануне
в `main` попало что-то сломанное, поэтому найди, что именно откатили, и скажи об этом.

Часть истории репозитория написана обычными предложениями, без Conventional Commits, — это ожидаемо
для старых коммитов и в риски не выносится. Смотри на то, что попало в окно отчёта.

Не превращай этот раздел в выговор: назови факт и его последствие, не давая оценок людям.

### 3.6. Открытые pull request'ы

Список получай инструментом `mcp__github__list_pull_requests` для `glav-kod/glav-lib`
с `state: "open"`. Чтобы ответ не раздувался, запрашивай только нужные поля:
`number`, `title`, `state`, `draft`, `html_url`, `user`, `created_at`, `updated_at`, `head`, `base`, `changed_files`.

Ветку конкретного PR забирай так (это работает и для веток из форков):

```bash
git fetch -q --force origin pull/<номер>/head:pr-<номер>
```

Для каждого открытого PR собери:

- **возраст** — сколько дней прошло с `created_at`;
- **простой** — сколько дней прошло с `updated_at`;
- **отставание от `main`:**

  ```bash
  git rev-list --count pr-<номер>..origin/main   # на сколько коммитов main ушёл вперёд
  git rev-list --count origin/main..pr-<номер>   # сколько своих коммитов в PR
  ```

- **реальный конфликт слияния.** Проверяй его не по полю `mergeable_state` из API, а расчётом:

  ```bash
  if git merge-tree --write-tree origin/main pr-<номер> >/dev/null 2>&1; then
    echo "конфликтов нет"
  else
    git merge-tree --write-tree --name-only origin/main pr-<номер> | tail -n +2 | sed '/^$/,$d'
  fi
  ```

  Ненулевой код возврата означает конфликт, а `--name-only` печатает список конфликтующих файлов
  сразу после строки с деревом слияния.

- **пересечение с тем, что менялось в `main` за окно.** Это отдельная и более коварная проблема, чем конфликт:
  merge может пройти чисто, а код при этом сломаться, потому что ветка правила файл исходя из его
  вчерашнего содержимого.

  ```bash
  git diff --name-only "$BASE" origin/main | sort > /tmp/main-files.txt
  mb=$(git merge-base origin/main pr-<номер>)
  git diff --name-only "$mb" pr-<номер> | sort > /tmp/pr-files.txt
  comm -12 /tmp/main-files.txt /tmp/pr-files.txt
  ```

  Непустое пересечение при отсутствии конфликта — повод сказать автору PR, что ветку стоит обновить
  и перепроверить именно эти файлы.

- **неотвеченные треды ревью** — `mcp__github__pull_request_read` с `method: "get_review_comments"`.
  Инструмент возвращает треды с полями `isResolved` и `isOutdated`; в отчёт идут нерешённые треды
  (`isResolved: false`), особенно те, где последний комментарий оставил рецензент, а автор не ответил.

Про PR в состоянии `draft` пиши отдельно и мягче: черновик, висящий неделю, — это нормально,
а вот готовый к ревью PR без движения — уже сигнал.

### 3.7. Сборка и тесты `main`

Перед прогоном переведи рабочее дерево на проверяемое состояние `main`, иначе результат будет
относиться не к тому коммиту, о котором отчёт:

```bash
BRANCH=$(git rev-parse --abbrev-ref HEAD)
git checkout --detach origin/main

dotnet build GlavLib.sln -c Debug
dotnet test GlavLib.SourceGenerators.Tests/GlavLib.SourceGenerators.Tests.csproj
dotnet test GlavLib.Tests/GlavLib.Tests.csproj --filter 'FullyQualifiedName!~GlavLib.Tests.Db'

git checkout "$BRANCH"   # обязательно вернуть дерево в исходное состояние
```

Все три команды вместе занимают около минуты, так что дожидайся их полностью, а не сворачивай
проверку по таймауту. В `Directory.Build.props` включён `TreatWarningsAsErrors`, поэтому сборка
падает и от предупреждения — если она упала на предупреждении, так и скажи, это чинится иначе,
чем ошибка компиляции.

Если `dotnet` не найден, значит SessionStart-хук облачной среды ещё не отработал: подожди или
запусти его вручную — `CLAUDE_CODE_REMOTE=true ./.claude/hooks/session-start.sh`.

**Тесты, работающие с базой, в облачной среде недоступны:** нет ни Docker, ни Postgres. Это
`GlavLib.Tests.Db.DbSessionFactoryTests` и весь `Sandbox/GlavLib.Sandbox.API.Tests`; фильтр
`FullyQualifiedName!~GlavLib.Tests.Db` отбрасывает первые, а второй проект просто не запускается.
В отчёте это надо оговаривать прямо — например, «тесты генераторов и тесты `GlavLib.Tests` без базы
прошли; тесты, требующие Postgres, не запускались». Выдавать частичную проверку за полную нельзя:
команда будет считать `main` проверенным сильнее, чем он проверен на самом деле.

**Известное падение.** В `GlavLib.Tests` без базы стабильно падают два теста —
`MultiLangMessageTests.It_should_format_message` и
`MultiLangMessageTests.It_should_ignore_argument_if_it_is_absent`. Причина в расхождении шаблона
и разбора: `MultiLangMessage.Format` подставляет аргументы по шаблону `{arg:type}`, а тесты
написаны на плейсхолдеры без типа. Пока эти два теста красные, отчёт называет их известными
и не выносит в риски; а вот их починка или появление третьего падения — новость, о которой
надо сказать.

## 4. Формат отчёта

Отчёт состоит из следующих разделов, именно в этом порядке.

1. **Итоги в цифрах.** Границы окна, число коммитов, число авторов, суммарный объём правок
   и разбивка по частям репозитория.
2. **Чем занимались.** Сгруппируй работу по темам — типы-значения, работа с базой, генераторы,
   HTTP-обвязка, песочница, инфраструктура сборки — и объясни в двух-трёх предложениях на тему,
   что изменилось и зачем. Не перечисляй коммиты подряд: список коммитов и так есть в истории,
   ценность отчёта в группировке.
3. **Публичный API и генераторы.** Что изменилось в публичных типах, выпускаемом генераторами
   коде, зависимостях пакетов и схеме базы. Если ничего из этого не менялось, так и напиши
   одной строкой — это тоже полезное знание.
4. **Риски и что проверить.** Не более **шести** пунктов, отсортированных по убыванию серьёзности.
   Каждый пункт — что именно не так и что с этим делать. Если рисков больше шести, значит какие-то
   из них не риски: оставь самые весомые.
5. **Открытые pull request'ы.** По одному абзацу или строке таблицы на PR: номер, тема, автор,
   возраст, простой, отставание от `main`, конфликты, нерешённые треды.
6. **Тесты.** Результат прогонов с явной оговоркой про недоступность тестов, требующих базы,
   и про два известных падения.
7. **Сборка `main`.** Прошла или нет, на каком коммите, с текстом ошибок, если не прошла.
8. **На что посмотреть завтра.** Короткий список того, что должно сдвинуться: зависший PR,
   ломающая правка API без упоминания в описании, упавший тест.

Жёсткие ограничения формата:

- **Построчный пересказ diff'а запрещён.** Кто какую строку поменял, видно в самом diff'е;
  в отчёте нужен смысл изменения.
- **Раздел рисков — максимум шесть пунктов.** Длинный список рисков не читают, и настоящая
  проблема тонет среди мелочей.
- **Полные предложения.** Действуют правила `.claude/rules/language-russian.md`: без телеграфного
  стиля, без обрывков вида «фикс сериализации», без цепочек стрелок `A → B → C`. Технические
  идентификаторы — имена файлов, классов, методов, таблиц — оставляй на английском в бэктиках.
- **Ссылки на коммиты и PR** давай в виде `#42` и коротких хешей, чтобы GitHub их подсветил.

## 5. Публикация

Отчёт публикуется **новой issue** в репозитории `glav-kod/glav-lib` на каждый запуск — инструментом
`mcp__github__issue_write` с `method: "create"`.

- **Заголовок** — вида `Отчёт по репозиторию за 5 августа 2026`, с датой окна (не датой запуска,
  если они разошлись) прописью по-русски.
- **Метка** — `daily-report`. Проверить её наличие можно через `mcp__github__get_label`;
  если метки ещё нет, она создастся при создании issue, когда ты передашь её в параметре `labels`.
  Отдельного инструмента для создания меток в наборе нет.

**Пиши дельту, а не повтор.** Перед публикацией найди предыдущие отчёты через `mcp__github__list_issues`
с фильтром `labels: ["daily-report"]` и упорядочиванием по `CREATED_AT` по убыванию, прочитай последний
и сравни с тем, что собрал сегодня. Про то, что не изменилось, пиши изменением состояния:
«PR #42 висит уже 27-й день, за сутки без движения» вместо дословного повторения вчерашнего абзаца
про этот же PR. Дословный повтор обесценивает отчёт: его перестают читать.

**Пустой день — тоже отчёт.** Если за окно не было ни коммитов, ни изменений в открытых pull request'ах,
всё равно опубликуй короткую заметку: окно, «изменений нет», результат сборки и тестов `main`.
Отсутствие отчёта должно однозначно означать, что сломалось расписание, а не что день выдался тихим.
Для этого репозитория тихие дни — норма: библиотека меняется реже прикладных проектов, и короткий
отчёт про отсутствие изменений здесь ожидаем, а не является признаком неполной работы.

## 6. Ограничения для ежедневного агента

- **Ничего не менять в репозитории и ничего не коммитить.** Отчёт только читает состояние.
- **Не открывать pull request'ы**, не пушить ветки, не трогать чужие ветки.
- **Не писать комментарии в чужие pull request'ы** и не ставить им метки. Всё, что ты хочешь сказать
  про чужой PR, идёт в текст отчёта.
- **Вернуть рабочее дерево в исходное состояние**, если переводил его на другой коммит ради сборки:
  после `git checkout --detach origin/main` обязательно вернись обратно (`git checkout "$BRANCH"`)
  и убедись, что `git status --short` пуст.
- Локальные ветки `pr-<номер>`, созданные для анализа, оставлять не обязательно; если удаляешь их,
  удаляй только их (`git branch -D pr-<номер>`) и ничего больше.
