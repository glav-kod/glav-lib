# Комментарии в коде

Правило языконезависимое: оно действует везде, где пишется код, — C#, TypeScript,
JavaScript, шелл-скрипты, файлы сборки и конфигурации.

Код самодокументируем: понятное имя функции, переменной и класса объясняет происходящее
лучше любого комментария и, в отличие от комментария, не расходится с кодом со временем.
Очевидных комментариев — пересказывающих то, что видно из самой строки, — быть не должно.

```csharp
// ❌ BAD — пересказ атрибута и того, что и так известно про nullable reference types
// NullGuard проверяет только аргументы: возвращаемые значения и свойства оставлены
// на nullable reference types, которые ловят те же ошибки на компиляции, а не в рантайме.
[assembly: NullGuard(ValidationFlags.Arguments)]

// ❌ BAD — пересказ строки
// увеличиваем счётчик попыток
attemptCount++;

// ❌ BAD — комментарий вместо имени
// проверяем, что срок действия ключа центра не истёк
if (authority.NotAfter > dateTime)

// ✅ GOOD — то же самое сказано именем метода, комментарий не нужен
if (authority.IsKeyValidAt(dateTime))
```

```ts
// ❌ BAD — пересказ строки и заголовка функции
// хук загрузки списка сертификатов
export function useCertificates() {
  // фильтруем отозванные
  return data.filter(c => c.revokedAt === null);
}

// ✅ GOOD — имена сказали всё сами
export function useCertificates() {
  return data.filter(isActive);
}
```

```bash
# ❌ BAD — пересказ команды
# переходим в каталог backend
cd backend

# ✅ GOOD — без комментария
cd backend
```

Комментарий остаётся там, где объяснить нужно **сложный фрагмент или исключение
из общего правила**: ограничение внешней библиотеки, неочевидную ловушку, причину
отклонения от привычного решения. Такое объяснение почти всегда относится не к отдельной
строке, а к функции, классу или скрипту целиком — значит, его место в описании
на этом уровне: XML-doc в C#, TSDoc или JSDoc в TypeScript и JavaScript, шапка
в шелл-скрипте, — а не во врезке посреди тела.

```csharp
// ✅ GOOD — исключение объяснено на уровне метода
/// <summary>
/// Перешифровывает ключи всех удостоверяющих центров новым мастер-паролем.
/// </summary>
/// <remarks>
/// Запись идёт одной транзакцией и только после проверки: пока новый пароль не развернул
/// каждый ключ, рабочим обязан оставаться старый. Падение на середине иначе оставит
/// центры недоступными, а отката у этой операции нет.
/// </remarks>
public async Task<UnitResult<Error>> RotateAsync(string newPassword, CancellationToken cancellationToken)
```

Комментарий внутри тела уместен как исключение — когда странность локальна
и вынести её в описание функции нельзя.

```csharp
// ✅ GOOD — ловушка конкретной строки, к контракту метода отношения не имеет
// NHibernate падает на массиве: Contains уходит в MemoryExtensions и не вычисляется
// рефлексией при разборе дерева выражения.
var certificateIds = ids.ToList();
```

## Файлы сборки и конфигурации

Отдельно к ним относится ещё один вид очевидного комментария — пересказ назначения файла
или его места в раскладке. Имя и расположение файла говорят это сами:
`Directory.Build.targets` в корне решения по определению применяется ко всем проектам,
`Directory.Packages.props` по определению задаёт версии пакетов.

```xml
<!-- ❌ BAD — пересказ того, что следует из имени и расположения файла -->
<!--
  Общие настройки лежат в корне backend, а не в каталоге приложения:
  их читают и приложение, и тесты. В выходной каталог их кладёт этот блок.
-->
<ItemGroup Condition="'$(GlobalAppsettings)' == 'True'">
  <None Include="$(RootDirectory)appsettings.base.json">
    <CopyToOutputDirectory>Always</CopyToOutputDirectory>
  </None>
</ItemGroup>

<!-- ✅ GOOD — без комментария -->
<ItemGroup Condition="'$(GlobalAppsettings)' == 'True'">
  <None Include="$(RootDirectory)appsettings.base.json">
    <CopyToOutputDirectory>Always</CopyToOutputDirectory>
  </None>
</ItemGroup>
```
