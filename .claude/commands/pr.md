# Довести работу до pull request'а

Команду зовёт человек, когда считает ветку готовой показываться. Сам себе её агент
не назначает: сколько срезов лежит в ветке и закончены ли они — знает человек.

Порядок оформления коммита и pull request'а описан в `.claude/rules/git-workflow.md`.
Здесь — только то, чего в правиле нет: последовательность шагов и разбор случая,
когда работа оказалась не на той ветке.

## 1. Разберись с веткой

Выполни `git fetch origin` и посмотри, где лежит работа.

**Работа на рабочей ветке.** Обычный случай, ничего делать не нужно.

**Работа на базовой ветке** (`main` или та, от которой отведена работа). Так бывает,
когда сессия стартовала на базовой ветке и коммиты ушли прямо в неё. Коммиты при этом
локальные и не отправлены, поэтому чинится это штатно: работа переносится на новую ветку,
а базовая возвращается на своё удалённое состояние.

Молча так не делай. Сначала скажи человеку, что именно собираешься сделать, — сколько
коммитов переносишь, как назовёшь ветку, куда вернёшь базовую, — и дождись согласия:

> Перенесу 3 коммита на `fix/db-connection-leak`, `main` верну на `origin/main`. Продолжаем?

После согласия:

```bash
git branch <новая-ветка> && git reset --hard origin/<базовая-ветка>
```

Незакоммиченные правки в рабочем дереве переживают эту операцию, но проверь их наличие
до неё и скажи о них человеку: `git reset --hard` — из тех команд, последствия которых
хотят видеть заранее.

Имя ветки — `<type>/<краткое-описание>` латиницей, где `<type>` тот же, что в Conventional
Commits (`feat`, `fix`, `refactor`, `docs`, `chore`).

## 2. Закоммить и запушь

Незакоммиченные изменения закоммить по правилам `git-workflow.md` (Conventional Commits,
summary на русском, содержание — из реального diff). Затем запушь ветку.

## 3. Определи базовую ветку pull request'а

`main` по умолчанию не подставляй. Определи базовую ветку по подразделу «Базовая ветка
pull request'а» правила `git-workflow.md`. У уже существующего pull request'а базовую
ветку сверь и при расхождении поправь.

## 4. Создай или обнови pull request

Операции с pull request'ами — через `gh` CLI: `gh pr create --base <база>`, `gh pr edit`,
`gh pr view`. Многострочное тело передавай `--body-file` или heredoc.

Заголовок и описание — на русском. Шаблона pull request'а в репозитории нет, поэтому
оформляй описание тремя разделами — «Что изменилось», «Зачем» и «Как проверяли» —
по правилу `git-workflow.md`. Описание основывай на реальном diff ветки
(`git diff <базовая-ветка>...HEAD`), а не на памяти о сессии. Если правка затрагивает
публичный API библиотеки, схему базы данных или поведение source-генераторов, назови
это явно, отдельным абзацем. В секции «Как проверяли» назови запущенные команды и их
результат, а проверки, недоступные в облачной среде (всё, что требует Postgres), —
как непроверенные.

Pull request для этой ветки уже есть — обнови его заголовок и описание под текущий diff,
а не заводи второй.

## 5. Свяжи с тикетом

Работа шла по тикету — поставь в описание строку `Closes #<номер>`: при слиянии GitHub
закроет issue сам. Номер бери из аргумента команды, из имени ветки или из сообщений
коммитов.

Работа шла без тикета (правка объяснили словами) — строки `Closes` просто нет,
закрывать нечего.

## 6. Отдай ссылку

Скажи человеку, что сделано, и дай ссылку на pull request. Слияние — только **squash**;
если сливает человек в интерфейсе GitHub, при необходимости напомни об этом в описании.
