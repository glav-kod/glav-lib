# Исправить замечания ревью в pull request'е

Команду зовёт человек, когда оставил замечания к pull request'у и хочет, чтобы агент
их исправил. Ответов в обсуждениях агент не пишет: итог разбора человек читает в чате,
а закрытое обсуждение и коммит в истории pull request'а говорят сами за себя.

Порядок оформления коммитов — `.claude/rules/git-workflow.md`, обязательные проверки —
`.claude/rules/agent-verification.md`. Здесь только последовательность шагов.

## 1. Найди pull request

Номер передан аргументом — бери его. Иначе возьми pull request текущей ветки:

```bash
gh pr view --json number,url,headRefName,baseRefName
```

Если HEAD стоит не на ветке этого pull request'а, ничего не правь: скажи человеку,
на какой ветке ты стоишь и какая ветка у pull request'а.

Выполни `git fetch origin` и убедись, что локальная ветка не отстаёт от удалённой: если
человек или другой агент что-то отправил, сначала подтяни это (`git pull --ff-only`).

## 2. Собери открытые замечания

Нужны только **незакрытые** обсуждения: закрытые уже разобраны. `gh pr view` их статус
не показывает, поэтому читай через GraphQL:

```bash
gh api graphql -F owner='{owner}' -F repo='{repo}' -F number=<номер> -f query='
query($owner: String!, $repo: String!, $number: Int!) {
  repository(owner: $owner, name: $repo) {
    pullRequest(number: $number) {
      reviewThreads(first: 100) {
        nodes {
          id
          isResolved
          isOutdated
          path
          line
          comments(first: 50) {
            nodes { author { login } body createdAt }
          }
        }
      }
    }
  }
}' --jq '.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved == false)'
```

Замечание — вся ветка обсуждения, а не первый комментарий: последующие реплики часто
уточняют или меняют просьбу.

Замечания вне обсуждений по строкам тоже бывают — общий комментарий к pull request'у
и текст отзыва ревьюера. Посмотри их (`gh pr view <номер> --comments`) и учти те, что
оставлены после последнего коммита ветки.

Открытых замечаний нет — так и скажи человеку и закончи.

## 3. Разбери каждое замечание

Прежде чем править, открой код, на который указывает замечание, и пойми, о чём просят.
Замечание бывает вопросом («почему так?», «а это зачем?»): за ним обычно стоит просьба
убрать лишнее или назвать понятнее. Разбери, откуда взялось то, о чём спрашивают, и
исправь причину, а не добавляй комментарий с объяснением.

Если для решения нужны факты — как данные выглядят в базе, кто ещё вызывает метод, —
проверь их, а не предполагай. Найденное, что повлияло на решение, войдёт в итоговый отчёт.

Замечание не исправляй и обсуждение не закрывай, если:

- просьба неоднозначна и её можно понять по-разному с разными последствиями;
- исправление меняет публичный контракт — публичный API пакетов NuGet, схему базы данных
  или выпускаемый source-генераторами код — либо выходит за рамки pull request'а;
- ты не согласен с замечанием — например, исправление сломает поведение, которое
  проверяет тест.

Такие замечания вынеси в итоговый отчёт с вопросом к человеку.

## 4. Исправь и проверь

Правь только то, о чём просят замечания, — правило `.claude/rules/agent-scope.md`
действует и здесь. Если исправление тянет за собой соседний код (переименованный
класс встречается в тестах, изменилась сигнатура), правь и его.

Запусти проверки по `.claude/rules/agent-verification.md`. Тестовые проекты — по одному,
отдельными командами. Пока проверки не прошли, к следующему шагу не переходи.

## 5. Закоммить и отправь

Закоммить исправления по `.claude/rules/git-workflow.md`. Сообщение описывает, что
изменилось в коде, а не то, что исправлено замечание: «по замечаниям ревью» не пишется.
Несвязанные исправления раздели на отдельные коммиты.

Отправь ветку обычным `git push`. Перезаписывать историю (`--force`) нельзя: ревьюер
опирается на коммиты, которые уже видел.

## 6. Закрой обсуждения

Каждое исправленное обсуждение закрой — без ответа в нём:

```bash
gh api graphql -f threadId=<id обсуждения> -f query='
mutation($threadId: ID!) {
  resolveReviewThread(input: { threadId: $threadId }) { thread { isResolved } }
}'
```

Обсуждения, оставленные с вопросом к человеку (шаг 3), не закрывай.

## 7. Сверь описание pull request'а

Если исправления сделали неверным что-то в описании pull request'а — название класса,
состав изменений, секцию «Как проверяли», — обнови его через `gh pr edit` по шаблону
`.github/pull_request_template.md` (многострочное тело — через heredoc или `--body-file`). Если описание по-прежнему верно, не трогай его.

## 8. Отчитайся

Скажи человеку по каждому замечанию: что в нём просили, что сделано и почему так,
если решение неочевидно. Назови коммит, запущенные проверки с результатом и дай
ссылку на pull request. Отдельно перечисли замечания, оставленные открытыми, с вопросом
по каждому.
