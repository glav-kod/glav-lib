# Режим «сделай» (прямая реализация)

Эта команда **одноразовая**: она действует только на задачу, переданную ниже, и не
устанавливает роль на всю сессию. Когда задача доведена до PR, режим закончился —
в отличие от `/master`, который остаётся действующим до конца сессии.

Задача: $ARGUMENTS

## Главный принцип

**Фазы обсуждения нет.** Ты не собираешь ТЗ, не предлагаешь альтернативы и не ждёшь
согласия — ты сразу приступаешь к реализации. Команда рассчитана на багфиксы и мелкие
правки, где обсуждать нечего.

**Субагент не вызывается.** Весь код ты пишешь сам: изучаешь затрагиваемые файлы,
вносишь правки, проверяешь результат, коммитишь. Инструмент `Agent` и субагент
`executor` здесь не используются — это осознанное отличие от `/master`, а не упущение.

## Уточняющие вопросы

Разрешён **максимум один** блок уточнений, и только тогда, когда при неверном допущении
вся работа окажется бесполезной (например, непонятно, менять ли поведение существующего
публичного метода или добавить рядом перегрузку, — а от этого зависит, ломается ли код
у потребителей библиотеки).

Во всех остальных случаях вопросов не задавай: действуй, а принятое допущение назови
вслух в ответе — так пользователь сможет поправить тебя постфактум, не потеряв время
на переписку.

## Аварийный выход в `/master`

Если по ходу работы выясняется, что задача не мелкая, — остановись, не домысливай.
Признаки того, что нужно остановиться:

- решение упирается в выбор между вариантами, у которых **разные последствия**
  (разная архитектура, разный объём работ, разные компромиссы), и выбрать за пользователя
  нельзя;
- изменение **ломает публичный API** библиотеки: меняет сигнатуру, поведение или состав
  публичного типа, переносит тип между сборками, меняет состав зависимостей пакета.
  Библиотека выходит пакетами NuGet, и её потребителей агент не видит, поэтому ломающая
  правка обсуждается до реализации, а не после;
- изменение меняет **код, который выпускают source-генераторы**: их результат компилируется
  у потребителей, и правка шаблона расходится по всем приложениям сразу;
- изменение задевает **контракт HTTP-команд** — формат `ErrorResponse`, заголовки
  `X-Status` / `X-Debug`, порядок фильтров `CommandsFilter`, — то есть то, на что уже
  опираются клиенты приложений;
- изменение задевает **схему базы данных** (`migrations/`) или общие конвенции NHibernate
  из `GlavLib.Db/NhConventions/`: конвенция меняет имена таблиц и колонок сразу у всех,
  кто её подключил.

В этом случае объясни, что именно упирается в развилку и какие варианты видны, и предложи
перейти в режим `/master`, чтобы обсудить замысел до реализации.

## Порядок работы

1. **Изучи контекст.** Прочитай код, относящийся к задаче, и правила проекта
   в `.claude/rules/`, чтобы правка легла в стиль окружающего кода. Где что лежит —
   в `.claude/rules/project-map.md`.
2. **Внеси изменения.** Меняй только то, что нужно для задачи, соблюдая
   `.claude/rules/agent-scope.md` — в том числе запрет править сгенерированный код руками.
3. **Сведи документацию с кодом** (см. раздел ниже) — в том же изменении, а не отдельной задачей.
4. **Прогони проверки** (см. раздел ниже).
5. **Закоммить и запушь** изменения в рабочую ветку сессии. Сообщение коммита —
   Conventional Commits, на русском (см. `.claude/rules/git-workflow.md`).
6. **Создай или обнови PR** (см. раздел ниже) и дай пользователю ссылку на него.
7. **Выложи замечания вне объёма задачи** готовыми командами `/do` — по правилам раздела
   «Рамки задачи».

## Документация

Прежде чем коммитить, прочитай `.claude/rules/docs-update-policy.md` и приведи документацию
в соответствие с кодом в этом же коммите — по критериям и списку документов из правила.

## Проверки готовности

Перед завершением обязательно прочитай `.claude/rules/agent-verification.md` и выполни
оттуда проверки для затронутых частей репозитория. В режиме `/do` проверки прогоняешь
ты сам — код писал ты.

## Pull request

PR обязателен. **Отдельная просьба пользователя для этого не нужна.** В режиме `/do`
pull request создаётся или обновляется всегда — сам запуск команды `/do` и есть указание
довести работу до PR. Это требование имеет приоритет над общим правилом «pull request
создаётся только по явной просьбе пользователя»: здесь оно не действует. Останавливаться
после push и предлагать пользователю завести PR нельзя — задача считается выполненной
только тогда, когда PR создан или обновлён и ссылка на него отдана пользователю.

Порядок оформления pull request (заголовок, разделы описания, язык, стратегия слияния,
инструменты GitHub MCP) описан в `.claude/rules/git-workflow.md`, раздел «Pull Requests», —
прочитай его и следуй ему.

До вызова инструментов GitHub MCP определи базовую ветку pull request'а по подразделу
«Базовая ветка pull request'а» того же правила: `main` по умолчанию не подставляй, а если
обновляешь уже существующий pull request — сверь его базовую ветку и поправь при расхождении.

## Рамки задачи

Держись рамок задачи по правилу `.claude/rules/agent-scope.md`: не рефакторь соседний код,
не переименовывай без необходимости и не чини молча замеченное вне объёма задачи.
В режиме `/do` такие находки оформляются так, как описано ниже.

### Замечания вне объёма задачи

Найденное вне объёма задачи не описывай общими словами в итоговом отчёте: сразу оформи
каждую находку как **готовую команду `/do`**, которую пользователь скопирует одним
движением и отправит в новый чат.

Правила оформления:

- одна находка — одна команда, каждая в отдельном блоке кода, чтобы её можно было
  скопировать целиком;
- команда самодостаточна: новый чат не видел ни этой сессии, ни diff. Назови файл и
  символ (класс, метод, конвенцию), в чём именно проблема и какого результата ждём;
- пиши по-русски, полными предложениями, без отсылок к текущей сессии
  («как обсуждали», «в рамках прошлой правки») — иначе в новом чате текст будет непонятен;
- объём команды — одна мелкая задача. Если находка тянет на развилку или ломает публичный
  API, так и напиши: это тема для `/master`, а не для `/do`;
- находок нет — ничего не выдумывай, просто не пиши этот раздел.

Пример вывода в конце ответа:

```
/do В `GlavLib.Db/NhUserTypes/JsonType.cs` метод `DeepCopy` копирует значение через
сериализацию в строку и обратно, из-за чего копия объекта стоит двух проходов JSON
на каждое сравнение состояния. Нужно понять, можно ли обойтись без сериализации,
и заменить реализацию, не меняя публичное поведение типа.
```
