# Рамки задачи

Правило действует для любого агента, который меняет код этого репозитория, — и когда
работа идёт по тикету через `/implement`, и когда её объяснили словами в разговоре.

## Не делай лишнего

Меняй только то, что нужно для поставленной задачи. Не рефакторь соседний код,
не переименовывай без необходимости и не добавляй улучшений, о которых не просили.

## Замеченное вне объёма задачи

Проблему, замеченную по пути и лежащую вне объёма задачи, не чини молча и не описывай
общими словами в итоговом отчёте: оформи каждую находку **готовой командой**, которую
человек скопирует одним движением и отправит в новый чат. Команда состоит из двух частей:
первым словом стоит точка входа — навык, которым эту работу заводят, — а дальше идёт
описание самой работы.

### Точка входа

Точка входа выбирается по природе находки, и выбор виден в самой команде: с какого навыка
начинается блок, с того работа в новом чате и начнётся.

- **`/grill-with-docs`** — находка тянет на развилку с разными последствиями либо задевает
  публичный контракт (публичный API пакетов NuGet, выпускаемый source-генераторами код,
  контракт HTTP-команд, схему базы данных). Такую работу начинают с интервью и спецификации,
  поэтому в тексте назови развилку или затронутый контракт — это и есть предмет проработки.
- **`/implement`** — остальные находки: способ исправления понятен, последствия не выходят
  за пределы правки.

### Текст находки

- Одна находка — одна команда, каждая в отдельном блоке кода, чтобы её можно было
  скопировать целиком.
- Команда самодостаточна: новый чат не видел ни этой сессии, ни diff. Назови файл
  и символ (класс, метод, компонент), в чём именно проблема и какого результата ждём.
- Пиши по-русски, полными предложениями, без отсылок к текущей сессии («как обсуждали»,
  «в рамках прошлой правки») — иначе в новом чате текст будет непонятен.
- Находок нет — ничего не выдумывай, просто не пиши этот раздел.

### Примеры

Обычная находка: понятно, что чинить и каким должен стать результат (файл и симптом
в нём вымышленные — важна форма записи).

```
/implement В `GlavLib.Db/Providers/ExampleProvider.cs` метод `OpenAsync`
не освобождает соединение, если открытие транзакции завершилось исключением, —
соединение остаётся занятым до конца жизни пула. Нужно освобождать его
в этом случае и закрыть поведение тестом.
```

Находка с развилкой и задетым публичным контрактом: решение выбирают до реализации
(файл и симптом тоже вымышленные).

```
/grill-with-docs В `GlavLib.Db/Providers/DbSessionFactory.cs` нет способа настроить
время ожидания подключения отдельно от времени ожидания команды — оба берутся из
одного места. Развилка: завести отдельный параметр тайм-аута подключения в конфигурации
`AddNpgsql`/`AddSqlite` или оставить один общий тайм-аут и документировать это
ограничение. Оба варианта касаются публичного API пакета: первый — совместимое
расширение, второй — только уточнение поведения.
```

## Сгенерированный код

Код, который выпускают source-генераторы (классы ошибок из `_errors/*.errors.yaml`, поля
`EnumObject`, методы регистрации сервисов `Add_<Assembly>`), руками не правь и в репозиторий
не коммить: он живёт только в `obj/` и пересобирается каждой сборкой. Меняется всегда исходник —
YAML-файл ошибок, атрибут `[EnumObjectItem]`, `[SingleInstance]`/`[Transient]` или сам генератор
в `GlavLib.SourceGenerators/`. Что именно генерируется и из чего — в `.claude/rules/project-map.md`,
раздел «Source-генераторы».

Отличие этого репозитория от прикладных проектов в том, что генераторы здесь и есть предмет
работы. Правка самого генератора — обычная задача, но тогда правится `GlavLib.SourceGenerators/`
вместе с тестами в `GlavLib.SourceGenerators.Tests/`, а не результат его работы у потребителя.
